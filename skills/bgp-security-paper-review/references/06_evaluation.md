# ⑥ Evaluation（实验与数据审计）

## 数据来源分类与代表性问题

对论文实验的每个数据集，先归类，再评估代表性：

| 数据源 | 特点 | 审计重点 |
|--------|------|---------|
| 现网测量（real-world measurement） | 稀有、高价值 | 抓取方法的偏差（vantage point、对等关系、覆盖）、时间范围、清洗规则 |
| 仿真（simulation） | 可控 | 拓扑真实性、BGP 模型保真度、参数是否贴合真实路由 |
| 测试床（testbed） | 真实设备/协议栈 | 规模有限、边界代表性 |
| 合成数据（synthetic） | 易控 | 是否闭门造车（生成的攻击是否符合真实攻击模式） |
| 回放（replay of real BGP data） | 用真实报文/RIB | 是否用真实时间序列、真实 AS 拓扑；回放粒度 |

**路由场景特有**：是否用真实 BGP update 流、真实 RIB/AS 拓扑、真实 ROA 覆盖/validator 分布？还是只做“理论图”？

## 可复现性（Reproducibility）

- 数据/代码/配置是否公开？公开到什么程度（论文声称 + 教程/版本 pinning）？
- 拓扑真相（ground truth）：实验里怎么知道“哪条路径是对的”？——很多路由测量论文的 ground truth 本身就是争议点（如用 RPKI 当 oracle，而 RPKI 覆盖不全）。
- 测量方法稳定性：同配置重跑是否得到相近结果（方差）？有没有统计处理？
- 依赖开源工具（bgpkit、pybgpstream、RPKI validator 等）的版本是否固定在正文/附录？

## 基线公平（Baseline Fairness）

逐条 check：

- 硬件：同一 CPU/网络环境？batch/优化代码优化程度对等？
- 参数：基线是否被调优到公平水平（而不是拿未调优的 baseline 衬托本方案）？
- 指标：是否用同一损耗量纲（如“验证开销”应固定安全等级与 key distribution）？
- 清除混杂：声称 “batch verification 更快” 时，必须**固定 key distribution，仅改变 verification strategy** 的对照，否则不可归因。

## 指标选择

- 路由安全场景的合适指标：控制面开销、收敛时间、CPU 验证开销、ROA invalid 处理率、可用性（可达性）、路径长度/路径选择扰动、报文膨胀（BGPsec 每个 hop 的额外字节）。
- 不合适指标：只报“检测率”不报误报率；只报总吞吐不报延迟分布；只报平均值不报尾部/最坏情形。

## 消融与负结果

- 每个贡献组件是否有消融（ablation）？去掉某组件后属性是否崩溃（可证明该组件必要）？
- 正负结果都呈现：哪些场景失败、哪些攻击绕过了机制 → 这直接决定 ③ 维“不保障什么”是否可信。
- 有没有“sanity check”（注入已知攻击验证检测器能发现它们）？

## 规模（Scale）与部署现实对应

- 路径验证类（BGPsec/ASPA/级联）：是否扩展到全互联网规模（百万级前缀 × 全网路径）的验证开销？
- 路由级联验证的最坏情形（最长路径、最坏前缀重叠）是否报告？
- 数据面影响：验证开销是否把转发面/收敛时间打到不可工程接受的水平？

## 输出到哪

`paper-review/experiment-audit.md`：数据集清单（来源/规模/时间/清洗）、可复现性评级（完全/部分/不可复现）、基线公平性表、指标合理性、消融/负结果检查；发现的对应 claim 缺口同步到 `claim-matrix.md`。
